# Architecture

This document describes how TANGENTA is built: the document model, the editor, rendering and the
import and export paths.

## Document model

A tree of `Node` objects, owned solely by the `Document`:

    document
    ├── masterPage      global object tree, visible on every page
    │   └── layer
    │       └── DrawObject …
    └── page …          page-specific object tree
        └── layer
            └── DrawObject …

- `canContain()` defines what may go where (pages only under the root, layers only in pages,
  drawing objects in layers and groups).
- Every node has a stable `NodeId` that is unique within the document. It stays the same across
  undo, redo, saving and loading. Tools and the UI remember ids, never pointers.
- All measurements are in mm, origin at the top left of the page, y pointing down.

## Drawing objects

Object-oriented: everything that can be drawn inherits from `DrawObject`. An object is a base shape
in local coordinates (`localPath()`) plus an affine transformation. Scaling, stretching, rotating and
skewing only change the transformation; a rotated rectangle remains a rectangle with a width and a
height. After rotation, the handles sit on the axis-aligned bounding box, and stretching a rotated
rectangle produces a parallelogram.

A group has no transformation of its own; transformations apply directly to its children.

A new object type needs: a subclass of `DrawObject`, `typeName()`, `localPath()`,
`writeProperties()`/`readProperties()` and an entry in `Serialization.cpp`.

## Undo/redo

No command pattern with hand-written inverses. Every change goes through a `Transaction` and is
recorded as data:

- `insert` records the inserted subtree,
- `remove` the removed subtree together with its position,
- `modify` the properties before and after.

Undo replays this data backwards, redo forwards. It is based on the same serialization as the file
format: what an object does not save, it cannot undo either, and the tests cover both together. A
transaction without `commit()` reverts its changes in the destructor.

Tools do not change the document while dragging. They show a preview and write exactly one undo
step on release.

## File format (.vek)

ZIP container (miniz, in the repo under `third_party/miniz`):

    mimetype        application/x-vektoreditor, uncompressed, first entry
    manifest.json   format and format version
    document.json   node tree as JSON

Files from newer format versions are rejected instead of being read halfway. Saving goes through
`QSaveFile`, so a half-written document never ends up on disk.

## Color

RGB only (sRGB, 8 bits per channel, with opacity). Deviation from the architecture reference: CMYK,
spot colors and separations are not planned. This also removes the need, for now, to separate the
screen renderer from the export renderer.

## Rendering

QPainter instead of Skia. It is sufficient for RGB and avoids the elaborate Skia build on both
platforms. The canvas only calls `path()` and `style()`; switching to Skia would stay confined to
`Canvas::paintObject`.

## Property bar and object-specific editing

Every object type describes for itself how it is edited: `DrawObject::propertyDescriptors()` returns
a list of `PropertyDescriptor` entries (length, angle, on/off, choice, command) with an icon and a
tooltip; `propertyValue()`/`setPropertyValue()`/`invokeAction()` implement them. The property bar
builds its controls from this list; every change runs as a transaction. A new object type thus gets
its own property bar without the UI having to know about it.

The rectangle is the first example: corner type (round, scalloped, chamfered), four corner radii,
linked or individual. As usual, scaling a rectangle that is not skewed transfers the scaling into
width and height, so that the radii are preserved in mm.

## Guidelines and snapping

Guidelines live on the master page (they apply to all pages), are saved with the document and can be
undone. The `SnapEngine` snaps to object nodes, object centers, object edges, guidelines and the page
edges/center; the snap radius is defined in screen pixels.

## Fills and gradients

`Fill` supports no fill, uniform fills and gradient fills (linear, radial, conical) with any number of
color stops. The gradient axis is relative to the local bounding box of the base shape (0..1), so the
gradient rotates, scales and skews along with the object. `GradientGeometry` translates this axis into
the terms of the classic dialog (angle, edge pad, center offset) and back. The fill is part of `Style`
and therefore applies to every drawing object; the Interactive Fill tool (G) drags the axis directly
on the object.

## Icons

Custom drawings, generated by `tools/make-icons.py` into `resources/icons/` and embedded in the
application. Add new icons there and run the script again; the test `allIconsRender` checks that
every icon is valid.
